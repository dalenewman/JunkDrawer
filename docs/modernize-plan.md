# JunkDrawer modernization plan

_Assessment: 2026-09-25. Implementation is underway. The portable solution, CLI, shared GUI, Mac64 launcher, native macOS and Windows host projects, SQLite/Excel and server integration tests, image build, CI, and packaging are in place. The Mac64 GUI launched and imported locally. Native macOS and Windows GUI launch, CI runs, and published multiarch manifest are still pending validation._

## Feasibility and target

**Feasible, with a substantial Transformalize integration rewrite.** The import concept and most file fixtures remain useful. A straightforward framework retarget would not have worked: at assessment all seven projects used old MSBuild projects targeting .NET Framework 4.5.2, `packages.config`, assembly hint paths, and, in some cases, Windows native copy steps. The custom import and paging pipeline has now been replaced by current Transformalize Autofac modules. The deliverables for this phase are a GUI that runs locally on this Mac and a Windows PC, a portable CLI, a multi-architecture Linux CLI image, CI, and documented NuGet packaging. Downloadable desktop app releases are a later phase.

Target shape:

| Component now | Proposed target | Notes |
| --- | --- | --- |
| `JunkDrawer` | SDK-style `netstandard2.0` library | Keep the reusable request, response, configuration, import and paging API if modern Transformalize types permit it. If they do not, target `net10.0` and document the reduced consumer reach. No .NET Framework target. |
| `JunkDrawer.Autofac` | SDK-style `netstandard2.0` library, subject to provider compatibility | Prefer composing current Transformalize Autofac modules; retire or rewrite the duplicated container and provider pipeline code. A `net10.0` target is acceptable if its dependencies require it. |
| `JunkDrawer.Console` | SDK-style `net10.0` executable | Preserve the useful `jd` arguments and XML arrangement behavior; run on macOS arm64, Windows x64, and Linux x64/arm64. The Linux build is also the container entry point. |
| `JunkDrawer.Eto.Core` | SDK-style `net10.0` or `netstandard2.0` UI library | Keep UI code shared between native platform hosts. Its TFM must be compatible with the chosen Eto package. |
| `JunkDrawer.Eto.WinForms` and `JunkDrawer.Eto.Core.Desktop` | One shared UI plus separate Windows, macOS native, and Mac64 host projects | `Eto.Platform.Mac64` provides a tested local arm64 Mac launcher without a workload. `Eto.Platform.macOS` remains an additional native backend requiring the matching .NET macOS workload. The Windows host uses Eto's Windows backend. Run the GUI locally on both computers; it is not part of the Linux container. |
| `Test` | SDK-style `net10.0` MSTest project(s) | Separate fast SQLite/fixture tests from database integration tests. |

`netstandard2.0` is a **library compatibility target**, not the app runtime. The executables and tests run on .NET 10. Choose it only where all referenced APIs and packages actually build. It is useful here because modern DateMath and much of Transformalize use it; it does not imply retaining a .NET Framework build. [Microsoft's .NET Standard guidance](https://learn.microsoft.com/en-us/dotnet/standard/net-standard).

## What the repository says today

- `JunkDrawer.sln` is a Visual Studio 2015 era solution. All seven `.csproj` files target `v4.5.2`; all use `packages.config`. `.nuget/NuGet.exe`, `.nuget/NuGet.targets`, root `nuget.exe`, and `JunkDrawer/JunkDrawer.nuspec` are legacy packaging paths. The nuspec version/dependency metadata is older than some project package references.
- Several projects directly reference `../../Transformalize` binaries or `packages/` DLLs. `JunkDrawer.Autofac` and `Test` run `xcopy` for SQL Server Compact native binaries. Those paths and post-build commands are not portable to Mac/VS Code.
- `JunkDrawer.Autofac/ImportModule.cs` and `Modules/AdoModule.cs` construct Transformalize pipelines and connection factories directly. The neighboring modern Transformalize tree now has provider-specific Autofac projects and no Access or SQL CE provider project. Its SQLite provider uses `Microsoft.Data.Sqlite`, MySQL uses `MySqlConnector`, and SQL Server uses `Microsoft.Data.SqlClient`. PostgreSQL provider projects target `net8.0;net10.0`, which may force the consuming Autofac project to `net10.0` if PostgreSQL remains included.
- The current `JunkDrawer.Eto.Core.Desktop/Program.cs` still imports `Pipeline.*` and uses older Eto packages than the WinForms launcher. Both launchers pass different `MainForm` constructor arguments. Do not assume either old host will compile with a package bump.
- `Test/Integration.cs` is NUnit 2.6.4 and includes hard-coded `C:\Code\...` paths, local SQL Server/PostgreSQL/MySQL credentials, SQL CE, and several useful `.csv`, `.xls`, and `.xlsx` fixtures. The test suite needs to be made portable before it can be a migration gate.
- `JunkDrawer.Console/Program.cs` resets `Environment.ExitCode` to zero at the end after some failure paths. Fix that while preserving CLI behavior.
- At assessment the Mac was arm64 with .NET SDK 10.0.103 and no .NET workloads. The native Eto macOS host needs a compatible workload and Xcode tooling. The new Mac64 launcher works without it. The original repository had no `global.json`, CI workflow, or modern build baseline; these have now been added.

## Dependency decisions to verify during implementation

| Area | Proposed action and compatibility check |
| --- | --- |
| Transformalize, Cfg-NET, DateMath | Use the **latest stable published NuGet versions**, including the latest compatible Transformalize core and provider packages; the current Transformalize/Autofac release is 1.5.0 as of this assessment. Start from the package names and project patterns in `../Transformalize`, `../DateMath`, and `../OrchardCore.Transformalize`, not the old `0.2.7-beta` references or local binaries. Use local `ProjectReference`s only temporarily for coordinated API work. Check Cfg-NET XML parsing and `Process` serialization behavior explicitly. [Transformalize on NuGet](https://www.nuget.org/packages/Transformalize), [Transformalize.Container.Autofac on NuGet](https://www.nuget.org/packages/Transformalize.Container.Autofac). |
| Autofac, logging, Dapper | Use current Transformalize registration patterns. Its sibling project references Autofac 9.1.0, and published `Transformalize.Container.Autofac` 1.5.0 requires Autofac >= 9.1.0. First make the spike work with the sibling's known versions; then try the newest stable Autofac release (9.3.2 as of this assessment) under the package update policy below. Pin 9.1.0 if a newer version fails a concrete compatibility test. Apply the same two-pass policy to logging and Dapper. Remove direct packages that become transitive or unused. [Autofac on NuGet](https://www.nuget.org/packages/Autofac), [Transformalize dependency list](https://www.nuget.org/packages/Transformalize.Container.Autofac). |
| File and Excel import | Test `.csv`, `.xls`, `.xlsx`, delimiter/header/type inference and code-page behavior with modern Transformalize file/Excel modules. Retain only direct `ExcelDataReader`, `FileHelpers`, `OpenXml`, `SharpZipLib` references actually called by JunkDrawer. |
| Database providers | First support SQLite, SQL Server, PostgreSQL and MySQL using the current Transformalize providers and connection factories. Remove SQL CE native binaries and its configuration/tests. Decide whether Access must remain a supported feature; its old provider is absent from the modern sibling and it should be documented as unsupported unless a separate supported implementation is found. |
| CLI parser | Replace `CommandLineParser 1.9.71` API with a supported parser (the modern Transformalize CLI uses `System.CommandLine`) or a small explicit parser. Preserve flag names, help and exit code semantics with CLI tests. |
| Eto | Eto.Forms 2.11 and `Eto.Platform.Mac64` provide a working .NET 10 arm64 Mac launcher without a workload. The project also retains an optional `Eto.Platform.macOS`/`net10.0-macos` host for the native workload path, and uses `Eto.Platform.Windows` for the Windows host. Verify file dialogs, grid paging, the SQL/log toggle, and minimum OS versions on both computers. The old MonoMac app template and GTK2 references have been removed. App distribution, signing and notarization belong to a later phase. [Eto project](https://github.com/picoe/Eto), [Eto.Forms package](https://www.nuget.org/packages/Eto.Forms), [Mac64 backend](https://www.nuget.org/packages/Eto.Platform.Mac64), [macOS backend](https://www.nuget.org/packages/Eto.Platform.macOS), [Windows backend](https://www.nuget.org/packages/Eto.Platform.Windows). |
| Package health | Establish a working spike with the sibling repositories' known versions, then, for **every** direct NuGet package, try the newest stable release available when migration begins. Verify target frameworks, transitive constraints, restore, build and relevant runtime tests. Do not retain an older version just because a sibling currently pins it. Record any package that cannot use the latest release, with the blocking dependency or test and the newest working version. Run `dotnet list package --outdated --include-transitive` (or the current SDK equivalent) and NuGet audit at each milestone; pin verified versions for repeatable builds. Do not infer runtime support solely from NuGet's computed compatibility table. |

The sibling repositories show two valid test configurations: DateMath and most recent Transformalize tests use `MSTest.Sdk` with Microsoft.Testing.Platform; OrchardCore.Transformalize still uses `Microsoft.NET.Test.Sdk` plus MSTest adapter/framework. Prefer the newer `MSTest.Sdk` pattern and its `global.json` runner setting for this conversion, adjusting the SDK version to a known working version at implementation time. For packaging, follow DateMath/Transformalize SDK-style `PackageReference`, package metadata, `dotnet pack`, and `scripts/nuget-pack.sh` discovery/version override rather than the old `.nuspec` file. Pack libraries only. Document the package IDs, version source, local pack command, artifact directory, package inspection, and the sibling's separate/manual NuGet push policy; do not publish packages as part of a normal build.

## Migration sequence and gates

1. **Baseline and decisions.** Inventory public APIs, CLI flags, XML arrangements, sample files, database targets and GUI functions. Record expected outputs from the README and fixtures. Include connection switching and the SQL/log toggle in the GUI inventory. Establish what Access/SQL CE removal means for users and how to report it. Create a branch; do not rely on the old solution as a working .NET 10 baseline.
2. **Minimal core and provider spike.** Convert only the projects and source needed to import one fixture CSV into a temporary SQLite database with modern Transformalize and Autofac. Use the sibling repositories' known dependency versions first. Verify generated table/view, inferred columns, row count and returned SQL; run a second import to test overwrite behavior. Map old Transformalize APIs to current interfaces and decide which custom modules can disappear. Gate: a minimal CLI can import and query SQLite on this Mac. If this requires substantial upstream API changes, scope those explicitly before converting the rest of the solution.
3. **Portable project skeleton.** Add `global.json`, `Directory.Build.props`, an SDK-style solution (retain `.sln` if useful for VS Code and Visual Studio), `PackageReference`s, package metadata, and copied fixture/resource rules. Remove assembly info duplicates, old NuGet restore artifacts, hint paths and Windows `xcopy` tasks. Settle direct package versions in a separate pass after the spike works. Keep warnings strict after the initial API port settles. Gate: the portable libraries and CLI restore/build on Mac and Windows with no .NET Framework targeting pack; each native GUI host has its own OS/workload gate.
4. **CLI and remaining formats.** Port argument parsing and XML arrangements; test delimiter, header and type options, bad input and nonzero failures. Add `.xls`/`.xlsx` fixture tests, including required code-page registration. Keep SQLite fixture tests in process. Verify the CLI and its SQLite native dependency on Linux x64/arm64 as well as Mac and Windows. Use the latest compatible `Testcontainers.MsSql`, `Testcontainers.PostgreSql`, and `Testcontainers.MySql` packages to start disposable databases for SQL Server, PostgreSQL and MySQL tests, following Transformalize's SQL Server Testcontainers pattern. Feed connection details from each started container into the test arrangement; isolate database names/files and clean up after each run. Run these tests in a separate CI job with a Docker-compatible engine; assess SQL Server image architecture on Apple Silicon and use an x64 runner where needed. Gate: all advertised providers have passing, automated integration tests without developer-local servers or checked-in credentials; unsupported providers fail clearly. [Testcontainers modules](https://www.nuget.org/profiles/Testcontainers).
5. **Eto GUI spike, then port.** Create a shared form with an Open dialog, log area and data grid. Launch the Mac64 host locally without a workload, retain a native `Eto.Platform.macOS` host for the workload build, and launch the Windows host on the Windows PC. Validate UI thread dispatch, background import, file dialog, paging, connection switching, the SQL/log toggle, and shutdown with the real `MainForm`. Run each GUI locally from its build and document exact commands and prerequisites. Gate: the same fixture can be imported and browsed through both local GUIs and the other retained functions work. The Mac64 host has launched and imported a fixture on this Mac; visual Mac and Windows interaction checks are still outstanding.
6. **Container image.** Containerize only the CLI, following `../Transformalize/src/CLI/Dockerfile` and `../Transformalize/.github/workflows/docker.yml`. Build `linux/amd64` and `linux/arm64` images on native GitHub runners, publish each by digest, then assemble one GHCR multi-architecture manifest. Start with the regular .NET runtime image; add the sibling's Alpine variant only after SQLite, Excel/code-page, globalization and provider tests pass on musl. Document bind mounts for input files, arrangements and SQLite output, working-directory/path behavior, container-to-database networking and passing credentials at run time. Gate: pulling the same image tag on both architectures and importing a mounted CSV into a mounted SQLite database succeeds; inspect the manifest and scan the published image.
7. **Packaging, CI and documentation.** Package only the reusable libraries with correct dependencies, README, license and version metadata. Add `CHANGELOG.md` now and update its Unreleased section as migration changes land; call out changed public APIs, CLI behavior and supported providers before a release. Follow `../Transformalize/scripts/nuget-pack.sh` and its NuGet workflow for packable-library discovery, explicit package versions and inspectable `.nupkg` artifacts; keep NuGet push manual and separate. Add `docs/packaging.md` with package IDs, versioning, local pack/inspection steps, output paths and how a maintainer would publish when ready. Model PR/push build and test and GHCR image workflows on `../Transformalize/.github/workflows/`, adapting project paths and permissions. CI jobs restore/build/test the portable projects on macOS, Windows and Linux; native GUI jobs build on their own OS, with the macOS workload installed. Keep database integration tests in separate Docker-backed jobs. Gate GHCR image publishing on successful build/tests. Update README paths, screenshots, OS/workload prerequisites, supported providers, container use and local run commands for VS Code and Visual Studio Community. Gate: a clean checkout builds/tests on supported hosts; both local GUIs and the CLI image pass smoke tests without old NuGet or .NET Framework tooling. Downloadable desktop app archives, signing and notarization are deferred.

## Completion criteria

- No project targets `net4*`, uses `packages.config`, relies on a checked-in `nuget.exe`, or copies SQL CE binaries.
- `dotnet restore`, `dotnet build`, `dotnet test`, and `dotnet pack` (libraries) succeed from a clean checkout on their supported hosts; native GUI projects use their OS-specific workload jobs, and package audit has no unexplained findings.
- CLI imports fixture CSV and Excel files into SQLite on Mac, Windows and Linux, emits useful errors and correct exit codes, and documents any changed behavior.
- Database integration tests cover every advertised server provider through Testcontainers where supported; credentials come from container setup or test infrastructure, never source files.
- Direct package references use the newest stable compatible NuGet releases, with any exceptions and their reasons documented.
- A single GHCR CLI image tag resolves to tested `linux/amd64` and `linux/arm64` images and imports mounted files; any Alpine variant passes the same tests before release.
- GUI starts and imports/browses data locally on this Mac and a Windows PC using maintained Eto backends; connection switching and the SQL/log toggle work.
- `CHANGELOG.md` records migration behavior changes, and `docs/packaging.md` explains reproducible library packaging and the separate manual NuGet publishing process.
- Public package/API changes and dropped Access/SQL CE support are called out in release notes before a major version is published.
